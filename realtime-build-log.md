# Realtime — Build Log

Chronological record of what actually happened during implementation — framework surprises, real bugs caught by testing, and the reasoning behind each fix. Kept deliberately separate from `realtime-architecture-spec.md` (intended design) and `realtime-roadmap.md` (planned scope): this is the "what we actually hit and how we resolved it" record. Updated every milestone.

---

## M0 — Bootstrap

- **Stack lock-in updated:** the original plan pinned Spring Boot 3.3.x. By the time building started, 3.3, 3.4, and even 3.5 had all exited open-source support. Moved to **Spring Boot 4.1.1** — current supported line, Java 21 baseline unchanged from the original plan.

## M1 — Ingest-to-Stream Core

- **Redis bean collision (not actually a Boot 4 issue):** a custom `ReactiveRedisTemplate<String,String>` bean named `reactiveRedisTemplate` collided with Spring Data Redis's own auto-configured `reactiveStringRedisTemplate` bean — both assignable to the same generic type, causing `NoUniqueBeanDefinitionException` the moment a real constructor injection (`IngestService`) exercised it. This conditional-bean-by-name behavior has existed in `RedisReactiveAutoConfiguration` since Spring Boot 2.0; it simply had no injection point to break until M1. **Fix:** name the bean `reactiveStringRedisTemplate` directly, satisfying Boot's `@ConditionalOnMissingBean(name=...)` check so the duplicate is never created.
- **Boot 4 test-slice starter split:** `@WebFluxTest` requires `spring-boot-starter-webflux-test` as a separate dependency now — test-slice starters were split out of the monolithic `spring-boot-starter-test`.
- **Package move:** `@WebFluxTest` relocated from `org.springframework.boot.test.autoconfigure.web.reactive` to `org.springframework.boot.webflux.test.autoconfigure`.

## M2 — Live Fan-out + Gap-free Resume

- **Jackson 3 (Boot 4's new default JSON library):** package root moved `com.fasterxml.jackson` → `tools.jackson`; the checked `JsonProcessingException` was replaced by an unchecked `JacksonException`. `ObjectMapper` is now an *abstract base class* — the concrete JSON implementation is `JsonMapper` (`JsonMapper extends ObjectMapper`), mirroring the existing `XmlMapper`/`CsvMapper` pattern. Injecting the supertype `ObjectMapper` still resolves correctly against Boot's auto-configured `JsonMapper` bean via ordinary polymorphism.
- **Ordinary Java inference gap:** `redis.opsForStream()` sometimes needed an explicit `<String, String>` type witness when chained into `Flux.defer(...)` — unrelated to any framework version, just a generic-method-in-a-lambda inference limit.
- **Deliberate scope deviation, tracked in spec §14:** shipped one independent `XREAD` loop per WebSocket session rather than the spec's shared-reader-per-channel design. Correct by construction, less efficient at scale.

## M3 — Channel Filtering + Pipeline Hardening

- **RFC 9110 terminology update:** `HttpStatus.PAYLOAD_TOO_LARGE` deprecated in Framework 7.0 in favor of `CONTENT_TOO_LARGE`.
- **Wrong assumed exception type:** the actual exception WebFlux throws when `spring.codec.max-in-memory-size` is exceeded is `ContentTooLargeException` (replacing the now-also-deprecated `PayloadTooLargeException`), not `DataBufferLimitException` as originally assumed. Both extend `ResponseStatusException`, so the original bug wasn't "413 unhandled" — it was "413 handled by the general `ResponseStatusException` handler, with a null `getReason()` silently producing a null response message."

## M4 — Cold Archive + Retention

- **Spring Data Redis 4.1 gained native `XTRIM ... MINID` support** via `RedisStreamCommands.XTrimOptions`/`TrimOptions` — merged into the library only around October 2025. Verified against a real Redis instance before shipping, given how recent the API is. Both `XTrimOptions.of(...)` and `XTrimOptions.trim(...)` are real, equivalent static factories (`.of()` is a 4.1-added alias for `.trim()`).
- **Boot 4 modularization, again:** `FlywayAutoConfiguration` moved out of the monolithic `spring-boot-autoconfigure` into its own module. `flyway-core` alone is no longer sufficient — `spring-boot-starter-flyway` is required (confirmed via Spring's own "Modularizing Spring Boot" blog post, which describes this exact case).
- **Real logic bug (not a framework surprise):** `ReplayService`'s original hot/cold merge could return the same boundary event from both tiers — an inclusive Postgres `BETWEEN` up to `earliestHotId`'s own timestamp, combined with `hotRange` independently reading from `since`, both legitimately included the same event. Reproduced by hand-tracing the exact comparison logic (not just re-running the bug report), fixed by short-circuiting to hot-only when no gap exists, and strictly excluding the boundary ID from the cold slice when a gap does exist.
- **Known residual limitation, tracked in spec §14:** the cold-archive query keys off `receivedAt: Instant` (millisecond precision), which can't fully express a Redis stream ID's sequence-number-level exclusivity. Two events for the same channel landing in the exact same millisecond aren't perfectly disambiguated by a timestamp column alone.
- **Docker Compose startup race:** the app could start before Postgres/Redis were actually ready to accept connections. Fixed with `healthcheck` (`redis-cli ping`, `pg_isready`) plus `depends_on: condition: service_healthy`.

## M5 — Multi-Tenancy & Auth

- **New dependency risk assessed up front, not after a break:** JJWT needs a JSON provider (`jjwt-jackson` or `jjwt-gson`). Given Jackson 3's very recent, very disruptive package migration (M2), used `jjwt-gson` instead — Gson is a completely separate library, unaffected by anything Jackson-related. Verified `jjwt-gson` 0.13.0 is a real, current, actively-maintained artifact before committing to this choice.
- **Retired `ChannelRegistry` (M4's temporary stand-in), on schedule, not by accident.** `RetentionTrimmer` now sweeps every row in the real `channels` table instead. This closes spec §14 item 2 cleanly: since the webhook path now requires a real channel and a valid API key, there's no longer such a thing as an ad-hoc channel for the trimmer to miss.
- **Design decision, not explicitly specified in the original schema:** added `Channel.publicId` (a UUID) as the identifier that actually appears in every URL, keeping the auto-increment `id` purely internal. Sequential PKs in public APIs leak growth-rate information and make enumeration trivial — worth the small extra column even though the spec's original schema sketch didn't call it out.
- **Deliberate scope boundary, not an oversight:** `/ws/{channelId}`, replay, and filter-config endpoints remain unauthenticated after M5 — matches the roadmap's own explicit M5 ships list ("auth/data layer only"), tracked as spec §14 item 5, planned for M6.
- **Genuine open question flagged, not resolved by guessing:** whether `@WebFluxTest(WebhookController.class)` interacts with Spring Security's reactive auto-configuration for test slices — specifically whether it silently requires authentication for the whole slice, or ignores security entirely since `SecurityConfig` isn't explicitly imported. Not confident enough either way to add speculative fix code; if the pre-existing `WebhookControllerTest` cases fail after this milestone, this is the first thing to check.
- **Two non-obvious fixes caught by the compiler:**
  - `SecurityConfig.java` imported `SecurityWebFiltersOrder` from `org.springframework.security.web.server`. Checked directly: it's actually lived in `org.springframework.security.config.web.server` since Spring Security 5.0 (2017) — not a recent relocation like the other package moves in this log, just an incorrect guess from the start.
- **Lombok annotation processing stopped working silently between M4 and M5** (25+ "cannot find symbol" errors for generated getters/builders on every Lombok-annotated entity). Fixed with an explicit `<annotationProcessorPaths>` entry in `maven-compiler-plugin`, rather than relying on classpath auto-discovery. **Root cause only partially resolved:** every source checked ties this class of behavior to JDK 23+ disabling auto-discovery by default — but this project has run JDK 21 throughout, including M4, where the same Lombok annotations on `ArchivedEvent` compiled fine without this configuration. What actually changed between M4 and M5 to trigger this isn't fully pinned down (a `maven-compiler-plugin` version bump adopting stricter defaults independent of JDK version is plausible, given this project's parent POM consistently pulls very recent plugin versions — but not confirmed). The fix itself is correct and worth keeping regardless: explicit `annotationProcessorPaths` is the version-proof, universally-recommended way to configure Lombok either way.

## M6a — Close the Auth Gap + Pre-UI Hardening

An independent review surfaced most of what's in this section — each finding was verified against the actual code before being accepted, not applied on trust. See `realtime-architecture-spec.md` §14 for which of these closed a tracked limitation versus opened a new one.

- **Auth gap closed:** `/ws/{channelId}` now requires a JWT via `?token=` query param (browsers can't set custom headers on a WS handshake, so the header-based mechanism the rest of the app uses can't gate this path) — validated and tenant-checked inside `ChannelWebSocketHandler` via a new `ChannelAccessService`, reusing `ChannelService.requireOwnedChannel` rather than duplicating the ownership check. Replay and filter-config are ordinary REST endpoints, so they just needed the same `Authorization: Bearer` pattern already used by channel CRUD, plus that same `requireOwnedChannel` call. `SecurityConfig` simplified as a result — every `/channels/**` path now uniformly requires authentication at the Security layer, with tenant *ownership* (as opposed to mere authentication) checked at the service layer.
- **Missing transaction boundaries — confirmed real, not just theoretical.** `AuthService.signup` and `ChannelService.create` each do two related saves (tenant+user, channel+API key) that need to succeed or fail together. Spring Data JPA's `SimpleJpaRepository.save()` is transactional at the *method* level, so two separate `.save()` calls each get their own transaction — a failure between them leaves an orphan. Fixed with `TransactionTemplate`, not `@Transactional`: both methods run inside `Mono.fromCallable`, called from within the same class — a self-invocation that Spring's AOP proxy doesn't intercept, which would make a plain `@Transactional` annotation silently do nothing.
- **`ON DELETE CASCADE` added to `api_keys.channel_id`** (V3 migration) — deleting a channel previously threw `DataIntegrityViolationException`, since every channel has an active key referencing it with the default (non-cascading) FK behavior.
- **TOCTOU race on signup email uniqueness** — the `findByEmail` check has a window a concurrent duplicate signup can slip through, surfacing as an unhandled 500 from the database's own unique constraint. Now caught and mapped to the same clean 409 the fast-path check already returns.
- **Login timing side-channel** — the original code skipped the (deliberately slow) BCrypt comparison entirely when an email wasn't found, creating a measurable timing difference that let an attacker enumerate registered emails without ever needing a password. Fixed by always running a comparison, against a fixed dummy hash when there's no real user.
- **Reactor NPE in `AuthService.login` caught during integration testing:** The timing-attack mitigation initially used `.map()` returning `null` when passwords mismatched or users were absent. In Reactive Streams / Project Reactor, `.map()` is strictly forbidden from returning `null` (Rule 2.13), which caused Reactor to throw an unhandled `NullPointerException` (HTTP 500) rather than passing down to `.switchIfEmpty()`. Fixed using `.<User>handle((maybeUser, sink) -> ...)` which cleanly completes empty without emitting null, allowing `.switchIfEmpty()` to return `401 Unauthorized` as intended.
- **API key comparison switched to `MessageDigest.isEqual`** from `String.equals` — constant-time comparison is the correct primitive for comparing secrets, even though SHA-256 pre-hashing already limits how exploitable the timing difference would have been in practice.
- **`ArchiveWriter` hardened**: a hard cap on the in-memory buffer (drop + log at capacity, rather than growing unbounded if Postgres is down during sustained ingestion), and loop-draining until empty each scheduled cycle instead of one capped batch per cycle — the latter would fall permanently behind arrival rate above roughly 250 events/sec at the default settings.
- **Input validation added** (`@NotBlank`/`@Email` + `@Valid`) to signup/login/channel-creation DTOs, via the newly-added `spring-boot-starter-validation`. WebFlux's validation failures (`WebExchangeBindException`) already extend `ResponseStatusException`, so the existing `GlobalErrorHandler` catches them with no new handler needed.
- **Password-holding DTOs (`SignupRequest`, `LoginRequest`) given a custom `toString()`** that redacts the password field — Java records auto-generate a `toString()` over every field, which would otherwise put a plaintext password into any log line or exception message the object ever passed through.
- **Two items from the same review deliberately deferred, not fixed**: duplicate JSON re-parsing between `WebhookController` and `FilterEngine` (real, but the refactor cost exceeds the marginal benefit given typical payload sizes), and `RequestIdWebFilter` not respecting an incoming `X-Request-Id` from an upstream proxy (real, but only matters once a real proxy exists — M10's deployment — and the correct fix is more involved than a one-line change: the filter and `GlobalErrorHandler` would need to agree on a shared resolved-ID exchange attribute, since `exchange.getRequest().getId()` is immutable).
- **Filter operator not validated at write time — found in the same pass.** `ChannelFilterController.setRules` accepted any `op` string with no check. An unsupported one (a typo, or a client assuming richer syntax than v1 actually ships — see §5/§13) wasn't rejected until the next webhook happened to hit that channel's ingest path, where `FilterEngine.matches`'s `IllegalArgumentException` surfaced as an opaque 500 to whichever third party's webhook sender triggered it — not a 400 to whoever actually misconfigured the rule. Fixed by extracting the supported-operator set into a single constant used by both `matches()` and a new `validate()`, with `setRules` calling `validate()` before the rule list is ever stored, so a bad rule is rejected where it was written, not where it later happens to be evaluated.
- **Postgres-down burst test failed — a real regression, caught by manual testing, not by the earlier review.** Firing a burst of webhook events at a channel with Postgres stopped returned 500s, not the 202s spec §6/§9 explicitly promise ("ingest keeps working off Redis alone"). Root cause: `WebhookAuthService.authenticate` performs synchronous JPA lookups (channel by public ID, then its active API key) before `IngestService.ingest` is ever reached — a dependency that simply didn't exist when §9's guarantee was written at M4, introduced silently by M5's per-channel API-key check and never reconciled against it. **Not fixed here** — logged as spec §14 item 9 instead. The honest fix (a Redis-backed cache of active channel/API-key pairs, so ingest auth doesn't need a synchronous Postgres round-trip) is real design work that touches a stated delivery guarantee; it deserves its own deliberate pass, not a hasty patch folded into an already-large milestone.
- **One review item wasn't a bug**: the MIT license's `[Your Name]` placeholder is intentional — filling in a name I don't actually know would be worse than leaving it for the user to complete.

- **Self-inflicted process error, twice, worth naming plainly:** a `str_replace` call with a typo'd parameter name (`new_new_str` instead of `new_str`) silently deletes the matched content instead of replacing it, since the tool defaults an absent replacement to empty. Hit this twice in the same session — once deleting a row from the architecture spec's limitations table, once deleting the README's Status/Quickstart headers entirely. Both caught by immediately grepping for the expected new content after every edit rather than trusting the tool's "success" response at face value, and fixed before either was shipped.

## Between M6a and M6b — triage on the Postgres-down finding

- **Decision: defer spec §14 item 9 to M8, not fix it ahead of M6b.** No real webhook sender is pointed at this system yet, so there's no live exposure today. M8 already plans Redis-backed per-channel state on the ingest path (Bucket4j token buckets) — extending that same infrastructure to also cache active API-key hashes is the natural, lowest-friction place for this fix, rather than building a bespoke cache in isolation now under time pressure. The fix itself needs real design (cache invalidation on key revocation, specifically), not a quick patch. Revisit *before* M8 if a real sender gets onboarded first — that would change the risk calculus entirely.

## M6b — Dashboard

Stack changed from the roadmap's original "Thymeleaf + HTMX" to a TypeScript SPA (Vite + React + Tailwind) before any UI code was written — see `m6b-dashboard-blueprint.md` for the full reasoning. Backend additions below were needed regardless of which frontend stack was chosen; they're gaps the roadmap's own wording exposed once actually checked against the existing API, not consequences of the frontend decision.

- **`ChannelDto` carried no API key data at all.** The roadmap's "masked API key" display had nothing to render — `CreateChannelResponse` includes the raw key, but only once, at creation, by design. Added a `key_suffix` column (V4 migration) storing just the last 4 characters of the raw key, captured once at creation alongside the hash; `ChannelDto` now carries it. Doesn't touch `ApiKeyHasher`'s hashing/comparison logic at all — purely an additive, non-secret display field, same pattern Stripe/GitHub/AWS use for exactly this reason.
- **No endpoint existed for "send test event."** The naive approach — reuse the public `/webhook/{id}` path — can't work: the raw API key is shown once and deliberately never retrievable again. Added `POST /channels/{id}/test-event` on the existing, JWT+ownership-authenticated `ChannelController`, calling `IngestService.ingest()` directly — the same method the public path uses, so a test event goes through the same filter rules, dedup, and archival real traffic does. Response surfaces the real `IngestOutcome` (`ACCEPTED`/`FILTERED`/`DUPLICATE`) rather than the public path's always-202 shape — a testing tool that hides its own dedup/filter behavior from the person testing it isn't useful.
- **Genuinely bodyless request crashed the new endpoint — caught by manual testing, not by review or by the tests written alongside it.** `@RequestBody Mono<String>` with the default `required = true` throws `ServerWebInputException` for a request with no body at all (no `Content-Length`/`Transfer-Encoding`) — distinct from an explicit empty-string body, which resolves to `Mono.empty()` and flows through normally. The exception happens during argument resolution, before the handler method — including its own `defaultIfEmpty("")` fallback — ever runs. Fixed with `@RequestBody(required = false)` plus a null check. **This surfaced a second, unverified instance of the identical pattern in `WebhookController.receive`**, shipped since M1: its own "empty body" test (`blankBodyIsRejected`) only ever sent an explicit empty string, never a truly bodyless request, so the same latent crash was possible for a real third-party sender sending a genuinely empty POST. Fixed there too, with a test (`genuinelyBodylessRequestIsRejectedCleanlyNotWithA500`) that actually exercises the case the old test didn't. Extracted `WebhookController`'s private JSON-validation method into `JsonValidator` at the same time, once the new endpoint needed the identical check — one source of truth instead of two copies that could drift.
- **`SecurityConfig`'s deny-by-default catch-all (`anyExchange().authenticated()`) would have 401'd the dashboard's own static assets and shell.** Spring Security's filter runs in front of every request, including ones destined for the static-resource handler — without explicit `permitAll()` on `/`, `/index.html`, `/assets/**`, `/app/**`, and `/favicon.svg`, the login page's own JS bundle couldn't load, which is a chicken-and-egg problem no token could ever fix. Grants no access to actual tenant data — every real operation still goes through `/channels/**` (authenticated) or `/ws/**` (its own `?token=` check), unchanged. Caught in planning, before writing any frontend code, not by testing after the fact.
- Added `SpaController` (`/app/**` → `index.html`) so React Router's client-side routes survive a hard refresh — Spring's static handler has no concept of client-side routes.

Frontend foundation (auth flow, channel list/detail, live event panel, JSON tree viewer, test-event composer) built and verified with a real `npm run build` in the same session — see chat history for the design-token reasoning (deliberately not the near-black + acid-green combo that's become an AI-generated-dashboard tell).

- **Vitest worker timeout under Windows / Node 22 IPC:** Vitest's default `pool: 'forks'` failed to initialize child worker processes under Windows PowerShell. Switched to `pool: 'threads'` in `vite.config.ts`, restoring fast parallel unit testing.
- **Cross-browser ISO-8601 nanosecond precision fix (`EventRow.tsx`):** Java 21's `Instant.now().toString()` outputs 9 fractional digits (e.g. `.060092561Z`). While V8 (Chrome/Edge/Node) leniency silently ignores extra digits, strict ECMAScript parsers (Safari / WebKit on iOS and macOS) reject strings with >3 fractional digits, causing `Date.parse()` to return `NaN` (rendering as `NaNms`) and `new Date()` to return `Invalid Date`. Added regex-based truncation (`replace(/(\.\d{3})\d+/, (_, m) => m)`) and `Number.isNaN()` guards in `EventRow.tsx` with dedicated unit test coverage (`EventRow.test.tsx`).
- **Full Verification Suite Passed:**
  - Backend: 63/63 JUnit/Spring Boot integration tests passing.
  - Frontend: 12/12 Vitest tests passing (`EventRow` nanosecond/millisecond/fallback, `JsonTreeView` rendering/collapsing, `useChannelSocket` event queuing/pause-resume/cleanup/unauthorized handling).
  - Production build: `npm run build` generated static assets directly into `src/main/resources/static/` (gitignored).
  - End-to-end integration: Live Docker stack verified end-to-end (Signup -> Create Channel with key suffix -> WebSocket subscribe -> `POST /channels/{id}/test-event` -> real-time WebSocket frame reception).

## Between M6b and M6c — F-09 fix (expanded well beyond the two null checks originally scoped)

The peer-review triage doc estimated F-09 (null filter `field`/`value` → NPE) at two null checks. It ended up touching four files across three rounds, each caught by an actual `mvn test` run rather than by inspection alone — worth recording in that much detail, since two of the three rounds shipped something a static read of the diff would have called done and wasn't.

- **Round 1 — the named bug.** `FilterEngine.validate()` checked `op` but not `field`/`value`; a rule with either set to `null` passed write-time validation and then NPE'd inside `extract()`/`matches()` on whatever webhook next hit that channel — same shape as the M6a filter-op fix, just a field it wasn't extended to. Fixed with two more checks in `validate()`, plus regression tests calling `validate()` directly.
- **Round 2 — a null *rule element* and a null *rules list*, neither named by the finding.** A rule set like `[null, {...}]` still NPE'd (`validate()`'s loop called `rule.field()` on the null element before ever reaching the new checks) — fixed with an explicit `rule == null` guard in both `validate()` and `matches()`. Separately, `validate(null)` was made to return early (mirroring `matches()`'s existing "null rules = match everything" stance), but `ChannelFilterStore.setRules` still called `List.copyOf(rules)` unconditionally — `List.copyOf(null)` throws by contract, so a literal JSON `null` body now NPE'd one call later instead of inside `validate()` itself. Not a regression (both paths 500'd before this fix too), but a validate-looks-done trap: the test that would have caught it (`validate(null)` in isolation) doesn't exercise the controller→store call one line later. Fixed in the store, mirroring `getRules`'s own existing null-default (`getOrDefault(channelId, List.of())`).
- **Round 3 — the store fix from round 2 wasn't reachable from a real HTTP request.** A live `mvn test` run of the round-2 fix failed: `@RequestBody` defaults to `required = true`, and Spring treats a body that *deserializes* to `null` (a literal 4-byte JSON `null`, valid and present, just empty) the same as a body that's *absent* — `RequestResponseBodyMethodArgumentResolver` throws `ServerWebInputException("No request body")` before the handler method, and therefore before round 2's store fix, ever runs. This is the third occurrence of the exact same pattern already named twice in the M6b entry above (`ChannelController.sendTestEvent`, then retroactively `WebhookController.receive`) — evidently not an obvious failure mode even with two prior instances on record. Fixed with `@RequestBody(required = false)` on `setRules`, normalizing `null` to `List.of()` in the controller itself before calling `validate()`/`store.setRules()` — which makes the store's own null-safety from round 2 redundant for this one call path, but not for `ChannelFilterStore` used directly (a new `ChannelFilterStoreTest` exercises that independently, matching the "reachable only if a caller bypasses validate()" defense-in-depth this file already used for the operator check).
- **A fourth, unrelated bug fell out of broadening `extract()`'s catch clause.** The original code caught only `PathNotFoundException`; a malformed-but-non-null JSONPath (`"$[unclosed"`) threw an uncaught `InvalidPathException` instead, crashing ingest on every subsequent webhook to that channel — same failure shape as F-09, a different exception class, never named because it wasn't null-related. Widening the catch to `Exception` closed it as a side effect of adding write-time path validation (below).
- **Two proactive additions beyond the finding, not requested by it:** `FilterEngine.MAX_RULES_PER_CHANNEL` (50) caps rule count per channel, and `validate()` now compiles each rule's `field` via `JsonPath.compile()`, rejecting an invalid path with 400 instead of letting it silently never-match at evaluation time. Both are judgment calls, not measured ones — tracked as spec §14 row 10, open, pending real load-test data.
- **Also filtered defensively, not because a live path needs it:** `ChannelFilterStore` now no-ops on a null `channelId` and strips null elements from a rules list rather than trusting every caller to pre-validate — neither is reachable via HTTP (`@PathVariable` can't be null; `validate()` already rejects a null element before `store.setRules` is ever called), but both are exercised directly by `ChannelFilterStoreTest` as the store's own standing invariant, independent of who calls it.
- **Verification, three rounds deep:** 101 backend tests (`FilterEngineTest` 9→26, `ChannelFilterControllerTest` 0→15 new, `ChannelFilterStoreTest` 0→8 new), 12 frontend Vitest tests, and a live Docker-stack smoke test covering all eleven filter-validation cases plus the max-rules and malformed-JSONPath checks — `docker logs` confirmed clean structured 400s, zero 500s/NPEs, across the full run.

## M6c (Batch 1) — F-01: Redis Stream Approximate MAXLEN Cap

The first item of the M6c pre-M7 correctness and hardening batch addresses the missing approximate `MAXLEN` cap on the Redis Stream ingest path (spec §3, `Peer-Review.md` F-01).

- **Spring Data Redis 4.1.1 API verified:** `ReactiveStreamOperations.add(K, Map, XAddOptions)` natively supports atomic appending with trimming options via `RedisStreamCommands.XAddOptions.maxlen(long).approximateTrimming(boolean)`. This emits native `XADD stream:channel:{id} MAXLEN ~ <cap> * payload <rawBody> received_at <instant>` in a single round-trip, requiring no custom Lua scripts or secondary `XTRIM` calls.
- **Configurable cap with fallback:** Added `realtime.archive.stream-maxlen: 50000` to `application.yml` under `realtime.archive` and injected into `IngestService` via `@Value("${realtime.archive.stream-maxlen:50000}") long streamMaxlen`.
- **Fail-fast startup validation:** Added defensive validation in `IngestService`'s constructor (`if (streamMaxlen <= 0) throw new IllegalArgumentException(...)`), ensuring invalid environment or profile overrides fail immediately at startup with an explanatory message rather than at runtime write time.
- **Deliberate scope boundary maintained on Docker Compose (`docker-compose.yml`):** Reverted experimental `--maxmemory 256mb` flags on the compose Redis container. At ~25MB per channel at the 50k cap, an unmeasured 256MB dev limit would cause Redis to refuse writes with OOM after just ~10 channels under `noeviction`. Sizing Redis memory and formalizing eviction/persistence requirements is explicitly owned by **F-14 (M10)** against real load-test measurements.
- **Spec §14 kept clean as an active gap tracker:** Kept spec §14 focused strictly on active unresolved technical debts and open deviations, rather than accumulating permanently resolved review findings. `Peer-Review.md` and this build log carry the permanent resolution history.
- **Isolated unit tests added (`IngestServiceTest`):** Closes the `IngestService` portion of F-20 with 4 comprehensive unit tests: constructor rejection on non-positive cap, rigorous property assertions on the captured `XAddOptions` (`hasMaxlen() == true`, `getMaxlen() == 50000`, `isApproximateTrimming() == true`), `ArchiveWriter.enqueue()` verification on accepted events, duplicate fingerprint drop with no stream/archive writes, and filter drop with no dedup/stream/archive writes.
- **Live wire-level verification against running Redis (`IngestServiceLiveRedisTest`):** Proved that `IngestService.appendToStream()`'s `XAddOptions` actually transmits `MAXLEN ~` over the wire through Lettuce Netty pipelines to the Redis 7 engine. Bursting 300 distinct events through `IngestService` into live Redis with a test cap of 100 yielded a final `XLEN` of **143** — well below the untrimmed 300, confirming trimming actually occurred on the wire, not just in the Java-level options object. The assertion deliberately doesn't pin an exact upper margin above the cap: approximate trimming only releases whole macro-nodes (Redis's documented default `stream-node-max-entries` is 100, an internal detail outside `XADD`'s contract and not something a test should assume), so the exact post-trim length is expected to vary by run — the test checks `xlen >= cap` (never over-trims) and `xlen < totalEvents` (growth wasn't unbounded), which is the actual acceptance criterion, without risking flakiness from guessing Redis's internals.
- **Verification:** 106/106 tests passing cleanly across unit and live integration suites (`mvn test`).

## M6c (Batch 2) — F-08: Format Validation on `since` and `last_id` at REST/WS Boundaries

The second item of M6c addresses uncaught `NumberFormatException` and out-of-range database/protocol errors when clients pass malformed stream IDs (`since` on the REST replay path, `last_id` on the WebSocket resume path), which previously surfaced as opaque 500s or unhandled event-loop connection breaks (`Peer-Review.md` F-08).

- **Single source of truth via `StreamIds.isValid(String id)`:** Rather than duplicating regexes or validation logic between `ReplayController` and `ChannelWebSocketHandler`, `StreamIds.isValid` delegates directly to `StreamIds.parse(id)`. Reusing the same "reject where written" pattern established in M6a/M6b, validation and parsing can never drift.
- **Hardened canonical stream ID regex (`CANONICAL_PATTERN`):** Standard `Long.parseLong` allows negative values (`-5`) and explicit plus signs (`+1000`). Enforcing `^\d+(-\d+)?$` directly in `StreamIds.parse` eliminates subtle loopholes like `1000--5`, which previously returned true and then crashed Redis `XREAD` with `ERR Invalid stream ID specified as stream position` (HTTP 500).
- **Postgres `TIMESTAMPTZ` upper bound guard:** While Java `Instant.ofEpochMilli(Long.MAX_VALUE)` succeeds, PostgreSQL's `TIMESTAMPTZ` data type caps out at year 294,276 AD ($\approx 9.22 \times 10^{15}$ ms). Passing 16–19 digit millisecond values to JPA/Hibernate threw `PSQLException` with SQLState 22008 (`date/time field value out of range`), causing an unhandled 500 on the cold replay archive path. Enforcing `MAX_TIMESTAMP_MILLIS = 9_223_372_000_000_000L` in `StreamIds.parse` safely rejects extreme timestamps with 400 Bad Request at the API boundary.
- **WebSocket RFC 6455 control frame compliance:** Under RFC 6455 §5.5, control frame payloads (including Close frames) cannot exceed 125 bytes (2 bytes code + max 123 bytes UTF-8 text). Reflecting client-supplied input in close reasons risks exceeding this limit if multibyte UTF-8 characters are passed (e.g. emojis or CJK characters where length in code units does not match byte length), causing Netty to throw an unhandled `IllegalArgumentException` on the event loop and abruptly terminating the TCP connection. `ChannelWebSocketHandler` now emits an application close code of 4400 with the static reason phrase `"Invalid last_id format"`, cleanly mirroring the existing `4401 Unauthorized` pattern.
- **Tenant isolation order of validation preserved:** In both `ReplayController` and `ChannelWebSocketHandler`, channel existence and tenant ownership/authorization are strictly checked before cursor format validation. Malformed IDs against unowned or non-existent channels return 404 (REST) or 4401 (WS), preventing enumeration or information leaks.
